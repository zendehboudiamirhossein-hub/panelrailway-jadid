# Chop روی Railway

این پورت از همون پنل Chop است، منتها به‌جای Vercel Functions روی Railway
(یک پروسه‌ی Node.js عادی و درازمدت، نه سرورلس) اجرا می‌شه.

## چی عوض شد نسبت به نسخه‌ی Vercel

فقط لایه‌ی «ورودی/میزبانی». هیچ خطی از منطق برنامه (پنل، ساخت لینک VLESS،
محدودیت ترافیک/IP، بکاپ/بازیابی، ربات تلگرام، اسکن آی‌پی تمیز) در `src/`
تغییر نکرده.

- `api/server.js` (که Vercel خودش به‌عنوان Function صداش می‌زد) حذف شد.
- به‌جاش یک `server.js` در ریشه‌ی پروژه اضافه شد که همون `http.Server` رو
  می‌سازه، منتها با یک `server.listen(PORT)` صریح در آخرش — چون Railway
  (برخلاف Vercel) خودش کد رو صدا نمی‌زنه؛ باید خودِ پروسه گوش بده.
- `vercel.json` حذف شد؛ به‌جاش `railway.json` (اختیاری، فقط برای صراحت
  دستور استارت) اضافه شد.
- `package.json` یک اسکریپت `start` گرفت (`node server.js`).

## چیزی که واقعاً بهتر شد

چون Railway یک پروسه‌ی همیشه‌روشن اجرا می‌کنه (نه یک تابع سرورلس با عمر
محدود)، محدودیت‌های مستندشده‌ی نسخه‌ی Vercel از بین می‌رن:

- **بدون سقف ۳۰ دقیقه‌ای روی اتصال VLESS.** اتصال WebSocket تا وقتی خودِ
  کلاینت یا سرور نبنده‌ش باز می‌مونه؛ نیازی به reconnect دوره‌ای نیست.
- **نیازی به پلن Pro/Enterprise یا فعال‌سازی «Fluid Compute» /
  «Extended function duration» نیست** — این‌ها مفاهیم مخصوص Vercel
  Functions بودن و روی Railway اصلاً موضوعیت ندارن.
- **صورت‌حساب بر پایه‌ی مصرف واقعی منابع (CPU/RAM) کانتینرِ درحال‌اجراست،
  نه شمارش Function invocation** — برای یه پروکسیِ پرترافیک قابل‌پیش‌بینی‌تره.

## چیزی که همون‌طور مونده

- **بدون Durable Object، حالت روی Redis.** دقیقاً مثل نسخه‌ی Vercel، چون
  Railway هم معادلی برای Durable Object نداره. باید یه Redis وصل کنی
  (پایین توضیح داده شده).
- **قابلیت «آی‌پی تمیز» (Cloudflare) هنوز فقط وقتی معنی داره که دامنه‌ی
  همین دیپلوی از طریق Cloudflare (ابر نارنجی) جلوی Railway پراکسی شده
  باشه** — دقیقاً همون منطق قبلی، چون این ترفند مال روتینگ SNI در شبکه‌ی
  Cloudflare است و به پلتفرم میزبانِ پشتش ربطی نداره. گزینه‌ی «Vercel» در
  همون دراپ‌داون اسکن آی‌پی هم دست‌نخورده باقی مونده (صرفاً یکی از حالت‌های
  تست، مستقل از این‌که خودِ برنامه کجا میزبانی می‌شه).

## پیش‌نیازها

- یه اکانت Railway.
- یه دیتابیس Redis. ساده‌ترین راه: توی پروژه‌ی Railway روی **+ New →
  Database → Redis** بزن. بعدش می‌تونی توی تنظیمات سرویس اصلی، متغیر
  `REDIS_URL` رو به‌صورت رفرنس بذاری: `${{Redis.REDIS_URL}}`
  (Railway خودش این مقدار رو از سرویس Redis پر می‌کنه).

## Environment Variables

توی تنظیمات سرویس Railway (Variables) این‌ها رو ست کن:

| متغیر | اجباری | توضیح |
|---|---|---|
| `REDIS_URL` | بله | آدرس اتصال Redis؛ اگه از پلاگین Redis خودِ Railway استفاده می‌کنی، `${{Redis.REDIS_URL}}` رو بذار |
| `ADMIN_PASS` | بله | رمز ورود پنل ادمین |
| `ADMIN_USER` | خیر | پیش‌فرض `admin` |
| `SESSION_SECRET` | بله (برای امنیت واقعی) | یه رشته‌ی تصادفی طولانی برای امضای کوکی سشن |
| `PUBLIC_HOST` | خیر | اگه دامنه‌ی سفارشی داری و می‌خوای لینک‌ها/سابسکریپشن دقیقاً همون دامنه رو نشون بدن |
| `PORT` | نه، خودکاره | Railway خودش این رو تزریق می‌کنه؛ لازم نیست دستی ست کنی |

## دیپلوی

### از طریق Railway CLI

```bash
npm install
railway login
railway init
railway up
```

### از طریق GitHub

1. این پروژه رو به یه ریپوی گیت‌هاب پوش کن.
2. توی Railway: **New Project → Deploy from GitHub repo**.
3. Railway به‌طور خودکار Node.js رو (از طریق Nixpacks) تشخیص می‌ده، `npm
   install` و بعد `npm start` (که همون `node server.js` است) رو اجرا
   می‌کنه — نیازی به تنظیم دستی build/start command نیست، ولی اگه بخوای
   صریح باشه همون `railway.json` این پروژه از پیش تنظیم شده.

بعد از اولین دیپلوی:

1. توی تنظیمات سرویس → **Networking**، یه دامنه‌ی عمومی بساز (یا دامنه‌ی
   سفارشی خودت رو وصل کن). WebSocket روی همون پورت HTTP کار می‌کنه، نیازی
   به تنظیم جدا نیست.
2. با مرورگر برو به `https://<دامنه‌ت>/` و با `ADMIN_USER`/`ADMIN_PASS`
   وارد شو.
3. یه کانفیگ بساز و لینک `vless://` رو با یه کلاینت تست کن.

## ربات تلگرام

بخش ربات تلگرام (webhook ساده‌ی HTTP، نه WebSocket) بدون هیچ تغییری کار
می‌کنه — از پنل → تب «ربات تلگرام» → توکن رو بذار و فعالش کن.
